# Contributing

## Getting started

1. Clone the repository. `.gitattributes` checks the extension source out with CRLF; a clone made before that rule existed needs `git rm -r --cached -q . && git reset --hard` once.
2. Open `XmlRecords.xif` in Integration Studio once. It unpacks the source to `XmlRecords/Source/NET`. Run Update Source Code (Extension menu) if `OutSystems.HubEdition.RuntimePlatform.dll` is not in its `Bin` folder: that puts the OutSystems platform assemblies there. The tests build against those assemblies, which are not in the repository.
3. To run the tests, install mono with Roslyn `csc` on macOS or Linux (`brew install mono`), or use Windows with the .NET Framework 4.8 targeting pack.

## Workflow

1. Create a branch from `main`, named after the release or the change, e.g. `fix/1.6.16`.
2. Make the change in the hand-written files: `XmlRecords.cs`, `RecordXmlSerializer.cs`, `RecordXmlDeserializer.cs`, `XmlSerializerConfig.cs`, `XmlSerializerAttributeConfig.cs` or `TypeMapper.cs`.
3. Update the tests in the same branch:
   - a fix makes the checks of its known issue pass: mark its entries `Fixed` in `tests/KnownIssues.cs` and move the issue to "Fixed" in `tests/KNOWN-ISSUES.md`;
   - add checks for any behaviour the existing ones don't cover, and prove they fail on the code before the fix;
   - expected values come from the specification (the action's description, the XML and ISO 8601 standards), never from the code's output. Don't change an expected value to make a failing check pass.
4. Run both targets. Each must end with `Failed: 0`:

       tests/run-tests.sh
       TARGET=source tests/run-tests.sh

5. Add the release to [CHANGELOG.md](CHANGELOG.md). Describe what changed for an app that uses the action, not how the code changed, and list behaviour changes separately.
6. Open a pull request against `main` and paste the two totals lines from step 4. There is no CI, because the platform assemblies can't be published with the repository.

## Releasing

1. Build the `.xif` in the release branch: open the previous release's `XmlRecords.xif`, put the changed source files back in `XmlRecords/Source/NET` (with CRLF line endings), then compile and save in Integration Studio **without publishing**. Reopen a fresh copy and check it unpacks exactly the repository's source.
2. Check the `.xif` isn't IP-protected: `istudio info XmlRecords.xif` must report `ipProtected: false`. Integration Studio stamps an environment's activation code into the file when it saves while connected to an IP-protected environment (a personal environment, for example, and every 1-Click Publish saves first). A stamped `.xif` can't be published to any other environment, so never commit one.
3. Commit the `.xif` in the pull request, and merge it once the tests pass.
4. Tag the merge `vX.Y.Z` and create a GitHub release with the `.xif` attached and the CHANGELOG entry as notes.
5. Before publishing, download the version that is on the server and compare its source with the previous release, so nothing published from elsewhere is overwritten. Then publish **a copy** of the `.xif`, so the committed file stays unstamped.
6. Upload the `.xif` to the Forge. The Forge already used 1.6.16 and 1.6.17 for the pre-fix DLL, so the Forge version can't always match the tag; give it the next free Forge number and name the tag in its release notes. Once it is there, replace `tests/lib/baseline/OutSystems.NssXmlRecords.dll` with the release's DLL, update the SHA-1 in `tests/lib/README.md`, and remove the `KnownIssues.cs` entries of the issues the release fixed.

## Code conventions

- Target .NET Framework 4.8 with C# 7.3 at most, like the existing code. The tests are C# 5, so they also compile under Windows PowerShell 5.1 `Add-Type`.
- `Interface.cs`, `Structures.cs`, `Records.cs`, `RecordLists.cs` and `Entities.cs` are generated by Integration Studio. Change actions, structures and their descriptions in Integration Studio, then copy the generated files here.
- Integration Studio only carries the files the `.xif` knows about, so a new source file is lost unless it is added to the extension's resources too.
- Convert values with `CultureInfo.InvariantCulture` unless a setting names a culture (TypeDecimalCulture).
- Don't depend on the wording of a .NET exception.

## Reporting issues

Include:

- the extension version;
- the OutSystems 11 platform version;
- the action, the structure, the XmlConfig and DefaultConfig used, and a small XML that shows the problem (with no real data);
- the full error message, or what happened and what you expected.
